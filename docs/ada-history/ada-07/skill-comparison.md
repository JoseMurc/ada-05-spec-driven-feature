# Comparación de Skills: Personalizada vs. Profesional

Comparación hecha sobre el mismo PR (#3, "Controlador interactivo") revisado por ambas skills:
- **Skill personalizada:** `reviewing-pull-requests` → resultado en `results/pr-readiness-review.md`
- **Skill profesional:** `code-review-and-quality` → resultado en `results/professional-skill-review.md`

## Tabla comparativa

| Dimensión | Tu Skill (reviewing-pull-requests) | Profesional (code-review-and-quality) | Conclusión |
|---|---|---|---|
| Trigger / routing | Se activa solo para revisiones de "PR listo para aprobar" (readiness review), antes de que un humano apruebe. | Se activa para cualquier revisión de código: antes de mergear, tras implementar, tras un fix, al evaluar código de otro modelo. | La skill personalizada es más específica al momento del flujo, mientras que la profesional cubre más situaciones de uso. |
| Scope / boundaries | Muy claro sobre qué NO hacer: no modifica código, no comenta/aprueba/mergea PRs, no escribe changelogs. Está pensada como un paso de solo lectura dentro de un proceso con documentos formales (REQUIREMENTS/SPEC/ARCHITECTURE/Traceability). | No define límites tan estrictos; asume que el revisor puede sugerir cambios de código, proponer refactors, y hasta decidir si "aprueba" el cambio. | La skill personalizada tiene fronteras más estrictas y apropiadas para un entorno académico con trazabilidad formal; la profesional es más flexible y adaptable pero menos controlada. |
| Workflow depth | Flujo de 10 pasos muy concreto: identificar rango de commits, leer documentos normativos, cruzar con matriz de trazabilidad, correr pruebas, clasificar hallazgos, generar reporte con plantilla, y validarlo con un script. | Flujo de 5 pasos más genérico (entender contexto, revisar pruebas, revisar implementación, clasificar hallazgos, verificar la verificación), pero agrega técnicas concretas como mutation testing manual y una tabla de severidades más granular. | La profesional aporta una técnica de verificación más rigurosa (mutation testing); la personalizada aporta trazabilidad formal con documentos del proyecto, ambas se pueden complementar aunque igual, la personalizada tiene un enfoque mas reducido y la profesional aplica revisiones en un enfoque mas amplios. |
| Correctness | Verifica que cada Acceptance Criteria tenga prueba, corre pytest y reporta el conteo real de pruebas. No incluye mutation testing. | Hace lo mismo, y además invierte condiciones en el código a mano (mutation testing) para comprobar que las pruebas realmente detectan errores, no solo que existen. | LA diferencia de la skill personalizada, la skill profesional  no solo confirma que hay pruebas, sino que esas pruebas sirven. Esto dio hallazgos más sólidos. |
| Architecture | No tiene una sección dedicada a arquitectura; se apoya en que ARCHITECTURE.md ya está actualizado y lo revisa por consistencia documental. | Tiene un eje completo de arquitectura con heurísticas puntuales (ej. ¿el refactor reduce complejidad o solo la mueve?, ¿hay lógica de feature en módulos compartidos?). | La profesional tiene más profundidad técnica en diseño de código; la personalizada se queda en si hay documentacion de arquitectura y si es consistente. |
| Security | No tiene un eje de seguridad explícito; seguridad se cubre indirectamente vía AGENTS.md (ej. no tocar datos fuera de alcance). | Tiene un eje de seguridad dedicado (validación de inputs, secretos, inyección, XSS, dependencias) con lista de verificación propia. | Para este PR no hubo hallazgos de seguridad en ninguna, pero la profesional está mejor preparada si el cambio tocara ese tipo de riesgo. |
| Performance | No tiene eje de performance; solo verifica que la prueba de latencia (NFR-01) siga pasando. | Tiene un eje de performance dedicado (N+1, loops sin límite, paginación) además de confirmar que la prueba de latencia sigue en verde. | Similar en este caso concreto porque el PR no tocaba rendimiento, pero la profesional esta mas preparada si hiciera falta. |
| Tests / verification | Corre pytest y reporta el resultado real (65/65), exige que no haya pruebas debilitadas o eliminadas. | Además de correr pytest, aplica mutation testing manual sobre el código nuevo (invierte condiciones y confirma que las pruebas fallan). | La profesional comprobó con evidencia que las pruebas realmente detectan errores, mientras que la personalizada solo confirma que pasan. |
| Severity model | 4 niveles ligados al proceso de aprobación: MUST FIX / SHOULD FIX / OPTIONAL / Human decision required. | 5 niveles ligados a si el autor debe actuar: Critical / (sin prefijo = requerido) / Nit / Optional-Consider / FYI. | Ambos modelos son razonables; el personalizado se enfoca decidir si el PR puede aprobarse,mientras que el profesional se centra en la urgencia de los comentarios. |
| Human review | Siempre termina pidiendo decisión humana explícita ("Human decision required: YES/NO"), nunca aprueba ni rechaza por sí misma. | Sí emite un veredicto final ("Approve" / "Request changes"), aunque aclara que la decisión última es humana. | La skill personalizada es más conservadora (nunca decide por el humano); la profesional se anima a dar un veredicto, lo cual es útil pero requiere más confianza en el agente. |
| References / composition | Usa archivos de referencia propios del proyecto: checklist, guía de severidad, plantilla de reporte, y un script de validación automática del reporte. | Hace referencia a otras skills relacionadas (`security-and-hardening`, `performance-optimization`, `constraint-driven-development`) para profundizar en cada eje. | La skill personalizada es más autocontenida y si bien eso le ayuda a no depender de nada, no es tan "escalable" con otras skills, por otro lado, la profesional está diseñada como parte de un ecosistema de skills que se apoyan entre sí. |
| Reusability | Muy adaptada a este proyecto específico: depende de que existan REQUIREMENTS.md, SPEC.md, ARCHITECTURE.md, docs/Traceability.md y AGENTS.md. Difícil de reutilizar en un proyecto sin esos documentos. | Es genérica ya que no depende de ningún documento específico del proyecto, funciona en cualquier repositorio con código y pruebas. | La profesional es más portable entre proyectos; la personalizada es más valiosa dentro de este curso porque obliga a mantener la documentación y trazabilidad al día. |

## Preguntas

**¿Qué hace la Skill profesional que tu Skill no contempló?**
Hace mutation testing manual: literalmente cambia una línea del código (por ejemplo invierte una condición) para comprobar que las pruebas existentes detectan ese error, y lo revierte después. Ademas de que cubre el rendimiento y la seguridad de manera mas fiable (no solo indica por encima), da un veredicto final de aprobacion/rechazo y se puede usar en general para "pre-aprobar" o revisar distintos "artefactos" de codigo y no solo PR's. 

**¿Qué elementos de tu Skill son más específicos al curso/proyecto y conviene conservar?**
La verificación cruzada contra REQUIREMENTS.md, SPEC.md, ARCHITECTURE.md y la matriz de trazabilidad (docs/Traceability.md), el respeto a las reglas de AGENTS.md (no tocar datos fuera de alcance, no debilitar pruebas, no modificar SPEC para forzar que pasen las pruebas), y el hecho de que nunca aprueba el PR por sí misma, siempre deja la decisión final a una persona. 

**¿Qué agregarías a una versión 2 de tu Skill?**
Agregaría el paso de mutation testing manual de la skill profesional, porque da evidencia más fuerte de que las pruebas realmente funcionan. También añadiría puntod explícitos de seguridad y rendimiento con su propia checklist, en vez de dejarlos implícitos dentro de AGENTS.md.

**¿Qué NO copiarías y por qué?**
Que la skill profesional de un veredicto final de "Approve" por sí sola. Para este curso prefiero que la skill siempre termine pidiendo una decisión humana explícita, porque el objetivo es apoyar al revisor, no reemplazarlo, y así se evita que alguien confíe ciegamente en la aprobación automática. Se podria ser mas flexible que la skill personalizada de puntos a favor o en contra pero no que apruebe directamente.

**¿Cuál produjo hallazgos más accionables? Incluye dos ejemplos.**
La skill profesional produjo hallazgos ligeramente más accionables porque están respaldados con evidencia experimental (no solo lectura del código). Dos ejemplos:
1. Detectó, mediante mutation testing, que si se invierte la condición de salida del bucle principal de la sesión interactiva, 13 pruebas fallan correctamente,confirmando que esa parte del código sí está bien cubierta por pruebas.
2. Encontró que ARCHITECTURE.md afirma que las pruebas no usan "monkeypatching global", pero una prueba específica sí lo hace (`monkeypatch.setattr("builtins.input", fake_input)`) para verificar el comportamiento por defecto. Es un hallazgo de precisión documental muy puntual que la skill personalizada no detectó porque no compara el texto de la arquitectura línea por línea contra cada prueba.

Por otro lado, la personalizada encontró dos hallazgos que la profesional no reportó, ambos relacionados con el historial de commits del proyecto (que la skill profesional no revisa con el mismo detalle): un commit sin referencia a su ID de tarea  y un merge commit inesperado dentro del rango de commits del PR. Son hallazgos accionables para este curso en particular, porque están relacionados a reglas explícitas del proyecto, pero no serían relevantes en otro contexto sin esas reglas.
